- [ ] **OI-51 — Optimistic locking is applied to some collaboratively-edited entities and not others, so the same artifact conflicts on one route and silently last-write-wins on another.** ✍️🧑 *Surfaced 2026-09-08 while fixing the peer-evaluation and RAM halves of OI-46, where the presence or absence of `@Version` turned out to decide whether a payload-supplied id was refused or honoured. **Code reality.** Six entities carry `@Version`: `RequirementDocument`, `DocumentSection`, `DocumentSectionLock`, `UseCase`, `UseCaseLock` and `ArtifactKeySequence`, all in RAM. Every other entity has none, including `RequirementArtifact`, `ArtifactLink`, `CommentThread` and `Comment`, and every foundation entity. `DocumentSectionService.updateDocumentSectionContent` and `UseCaseService.updateUseCase` both require an `expectedVersion` and answer a stale one with `OptimisticLockException`; `RequirementArtifactService.updateRequirementArtifact` and the three `GlossaryService` update methods take no version at all. **The concrete inconsistency.** A requirement artifact can be edited through at least three routes: `PUT /teams/{teamId}/requirement-artifacts/{id}`, the glossary `PATCH` routes, and as a list entry inside `PUT .../document-sections/{id}`. Only the last is version-guarded, and only at the section level. So two students editing the same artifact get a conflict error if they happen to go through the document section and silent data loss if they go through the artifact route, which is a difference in behaviour with no difference in intent. **The design question, which is the part that needs a decision.** Optimistic locking belongs on an aggregate root, not on every row: `UseCaseMainStep`, `UseCaseExtension` and `UseCaseExtensionStep` are children of `UseCase` and are covered by its version, exactly as `Rating` is covered by nothing today but would be covered by a version on `PeerEvaluation`. So the question is not "which entities lack `@Version`" but "what are the aggregate roots a user edits concurrently". The plausible answer for RAM is `RequirementArtifact` and `ArtifactLink`, and for the foundation probably none, since an activity and a peer evaluation each have exactly one author and course-level entities are edited by instructors one at a time. That reasoning should be written down and applied, rather than adding the annotation wherever it is missing. **Implementation trap, learned the hard way on 2026-09-08.** Adding `@Version` to an entity silently changes what Spring Data's `save()` does. `JpaMetamodelEntityInformation.isNew` consults a non-primitive version field *instead of* the id, so an entity with a null version is treated as new and takes `em.persist()` even when it carries an id, while the same entity without a version takes `em.merge()`. That is exactly why the OI-46 probe against `POST /teams/{teamId}/use-cases` came back as a 500 while the same attack on `POST /teams/{teamId}/requirement-artifacts` succeeded as a cross-team overwrite: `UseCase` has a version and `RequirementArtifact` does not. Adding a version to an entity therefore has to be checked against every create path that saves it, and is **not** a substitute for keeping payload ids out of converters, since a caller who sends a version field flips the branch straight back. **Scope if this is taken up:** a Flyway migration per entity for the new column, an `expectedVersion` parameter on the affected update methods, a conflict status code on the response, and a frontend change to round-trip the version. Do not fold it into OI-46; the two are independent, and OI-46's fix does not depend on any of this.*
