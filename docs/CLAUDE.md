# CLAUDE.md

This file governs edits to the **`docs/` spec chain** — the requirements, design, traceability, and methodology documentation that drives Project Pulse's implementation. It applies to `docs/requirements/`, `docs/design/`, `docs/traceability.md`, `docs/methodology.md`, and `docs/README.md`. `docs/product/` and `docs/guides/` are temporary non-spec material and are described separately below.

## What this directory is

`docs/` is the **spec→design→trace chain for Project Pulse** — the documentation chain that drives its implementation, organized **doctype-first**: one set of docs for the whole product, covering the original features — the shared foundation (courses/sections/teams) and performance tracking (weekly activity reports, peer evaluations) — and the RAM module. *This* file governs only **how those docs are authored and kept consistent**: anchors, ID schemes, file relationships, and cross-doc coherence. The repo-root `CLAUDE.md` governs the codebase as a whole and explains how this spec drives the code (its **Spec-driven development** section).

Layout of `docs/`:

- `requirements/` — the five core spec docs (below), plus `OPEN-ISSUES.md`.
- `design/` — the architecture-of-record plus per-UC-area design docs as they are generated.
- `traceability.md` — the whole-project spec→code traceability and coverage matrices.
- `methodology.md` — the spec-driven, agent-assisted development method write-up.
- `guides/` — supporting build guidance, not spec docs.
- `product/` — runtime product content Project Pulse seeds or uses, not a spec of Project Pulse.

The five core Markdown files under `requirements/` form a coherent set, best read in this order:

1. `requirements/project-glossary.md` — domain vocabulary; canonical definitions
2. `requirements/vision-and-scope.md` — business objectives (BO-*), risks (RI-*), assumptions (AS-*), major features
3. `requirements/use-cases.md` — behavioral specs ("The Student …", "The Instructor …")
4. `requirements/business-rules.md` — cross-cutting policies, constraints, and access rules (BR-*) cited by the use cases and the SRS
5. `requirements/software-requirements-specification.md` — functional requirements (FR-*), data model, quality attributes

Below, the five core docs are referred to by bare filename.

## Conceptual model to internalize before editing

The five spec docs are independent Markdown files, but they all describe **one shared model** of the Project Pulse domain — the same artifacts, terms, features, and rules seen from different angles. (The model itself is defined in the spec — start with the core graph model terms in `project-glossary.md` — not re-explained here.) So when changing one doc, check whether the same concept appears in another — they're supposed to agree because they describe the same underlying model:

- A **glossary term** added/renamed in `project-glossary.md` should be used consistently across the spec chain — the other four core requirements docs, `traceability.md`, and `design/` where applicable. Don't introduce a synonym for an already-defined term.
- A **feature** mentioned in `vision-and-scope.md` typically maps to use cases in `use-cases.md` and functional requirements in `software-requirements-specification.md`.
- **A use case is itself a (high-level) functional requirement.** That is why `use-cases.md` is referenced from the SRS's Use Cases section, under Functional Requirements. A use case's "The system …" steps plus its **Associated Information** are its detailed functional spec — so **do not restate a use case's flow (CRUD: create/view/edit/delete/search) as a separate FR.** When a use-case step needs more detail, elaborate it in that use case's Associated Information, not in a new FR. The SRS's **Non-Use Case Functional Requirements section is the complement**: only non-use-case, system-driven, event-driven, global, or background behaviors (autosave, locking, validation engine, real-time collaboration, AI/LLM orchestration, templates, terminology invariants, versioning, authorship metadata, security, export formatting, import, performance). The litmus test before adding a non-use-case FR: *is there a use case whose system-subject step already says this?* If yes, it belongs in that use case (or its Associated Information), not there — keep the bright line so that section never re-describes use-case behavior. Because the **use case is the unit of citation** — `traceability.md` carries one row per UC and tests are tagged to the UC, with no finer per-step handle — keep each use case right-sized so "UC-X is done / passing" is a meaningful statement (split a use case that grows large enough to half-satisfy rather than giving its steps sub-IDs), and write **extensions** precisely: with no step-level IDs, a use case's extensions plus their Associated Information are the only record of its negative/exception behavior, so they carry the edge-case requirements.
- Non-use-case functional requirement IDs use the format `FR-<AREA>-<slug>` — a descriptive area code, a hyphen, then a short kebab-case **name-based slug** derived from the requirement's own concept (unique within its area) — deliberately **parallel to the `UC-<AREA>-<slug>` use-case IDs**, and an identifier space independent of heading position. Because the handle is a name, not a number, inserting, removing, or reordering an FR renumbers nothing. The EARS-style non-use-case FR areas are: `FR-SAVE-*` autosave, `FR-VAL-*` validation, `FR-AI-*` AI, `FR-TPL-*` templates, `FR-GLO-*` glossary (terminology invariants), `FR-HIS-*` history & authorship metadata, `FR-SEC-*` security, `FR-NOT-*` notifications. (Behaviors that a use case fully captures get **no** non-use-case FR: section locking lives in the editing use cases' steps + `BR-edit-lock-required`/`BR-lock-expiry`, real-time collaboration lives in UC-COL-collaborative-edit, and document export and project-source import live in their use cases + the External Interface Requirements `SI-*`.) Reuse an existing area when adding a non-use-case FR; introduce a new descriptive area code only for a genuinely new non-use-case category that no use case can express. The only edit that costs anything is genuinely renaming a requirement's concept (rare, like renaming a heading) — update the inbound citations when you do.
- **Business rule IDs (`BR-*`)** live in `business-rules.md` and are flat `BR-<slug>` **name-based slugs** coined from each rule's gist (e.g. `BR-team-scoped-access`, `BR-review-lock`), unique across the doc and grouped thematically into sections. Like FR IDs, they are an **identifier space independent of heading position** — inserting a rule or moving a section renumbers nothing. A business rule is a *source* of requirements, not a built artifact, so it is **cited, never restated** as a parallel FR and gets **no row in `traceability.md`** (it is verified transitively through whatever cites it — the contrast with a non-use-case FR, which does get a row). Use cases cite them by ID in their **Business Rules** field; the SRS cites them where an FR or quality attribute enforces one. `/spec-build`'s *Business-rule coverage* check flags any rule **no** use case or the SRS cites (an orphan rule is dead policy or a missing requirement), and **regenerates** the backward *Business-rule enforcement index* in `traceability.md` (the `BR → {citing UC/FR/QS}` projection for change-impact analysis — generated from the forward citations, the one section of that file `/spec-build` may rewrite). A rule deliberately left to manual process, department policy, or instructor guidance rather than software is exempt **only** if its text ends with the marker `*(Advisory; not enforced by the system)*` (parallel to the `*(Platform-level emergent objective; …)*` carve-out for BOs); a *mixed* rule one of whose clauses IS system-enforced (e.g. `BR-active-weeks`) does **not** carry the marker and must still be cited.
- **Business objective IDs (`BO-<AREA>-<slug>`)** live in `vision-and-scope.md` and are area-prefixed by the capability the objective serves — `BO-PERF-*` (performance tracking) and `BO-RAM-*` (requirements authoring) — parallel to the `UC-<AREA>-<slug>` and `FR-<AREA>-<slug>` schemes, with a name-based slug after the area. This area-prefixing is applied **only** where an item is *owned* by one stable area. **Each business objective carries one or more success metrics (`SM-<slug>`, flat name-based slug)** — each with a baseline, target, measurement method, evaluation cadence — the *outcome → objective backward edge* (was the objective achieved, not just built?). Following the Wiegers & Beatty template, `vision-and-scope.md` keeps **objectives and their metrics in two sibling sections**: the **Business Objectives** section states each objective and names the SM IDs that measure it; the **Success Metrics** section defines each `SM-<slug>` and tags it back with the objective it measures. Each metric is defined once — in the Success Metrics section — and cross-referenced from its objective, never restated. Objectives are pitched at **strategic** altitude, so a single objective that decomposes into several measurable outcomes carries one `SM-<slug>` per outcome (e.g. `BO-RAM-requirement-quality` rolls up structural-quality, terminology-consistency, traceability-completeness, and navigation-usage metrics) — don't split one strategic objective into several BOs just to give each a metric. Each metric's evaluation route is recorded in `traceability.md`'s [BO measurement matrix](traceability.md#bo-measurement-matrix) (one row per metric), and `/spec-build`'s *BO-measurement* check flags any non-carve-out `BO-*` with no `SM-<slug>` (the `*(Platform-level emergent objective; …)*` BO is the lone carve-out).
- **Risks (`RI-*`) and assumptions (`AS-*`)** in `vision-and-scope.md`, and **business rules (`BR-*`)** in `business-rules.md`, stay **flat** `RI-<slug>` / `AS-<slug>` / `BR-<slug>` slugs (no area segment) precisely because they are *cross-cutting* — a risk, assumption, or rule applies across capabilities, so forcing it into one "owning" area would couple its identity to a fuzzy, reclassifiable judgment. Every ID in all these spaces is a **name-based slug**, not a number, so identity is decoupled from position: inserting or reordering renumbers nothing. The thematic grouping is organizational only.
- **Major features (`FEAT-<slug>`)** in `vision-and-scope.md` are likewise flat name-based slugs — a feature spans several use-case areas, so it carries no area segment. A feature is a **capability theme, deliberately coarser than a use-case area and never one-to-one with one**: each `FEAT-*` decomposes into use cases drawn from several areas (an area may also serve more than one feature). Do **not** add a feature that shadows a single area — coarsen it up into the theme that area belongs to — both to keep features at value-altitude (not a CRUD/substrate enumeration) and because the area is welded into every `UC-<AREA>-<slug>` ID, so a 1:1 feature would couple vision re-pitches to UC-ID renumbers. A feature's `### *FEAT-<slug>: Name*` H3 heading is its definition; the feature ↔ use-case-area map in `traceability.md` is **keyed to the ID**, and `/spec-build`'s *feature coverage* check verifies every `FEAT-*` has exactly one row there and every row resolves to a defined feature. Renaming a feature's display name changes its heading slug, so update any inbound `#anchor` link when you do — the ID handle itself stays stable.
- **Risk coverage:** like a business rule, every `RI-*` must be *justified* — either traced to a mitigating requirement/decision via its row in `traceability.md`'s [risk coverage matrix](traceability.md#risk-coverage-matrix), or consciously accepted with a trailing `*(Accepted; <rationale>)*` marker inline (the carve-out parallel to BR's `*(Advisory; not enforced by the system)*` and BO's `*(Platform-level emergent objective; …)*`). `/spec-build`'s *risk-coverage* check flags any risk that is neither — detecting acceptance by the marker only, never from prose.

## Authoring conventions

These files are the single source of truth for the project's requirements. Anchors, cross-references, and cross-doc terminology must stay consistent as the docs evolve. **Headings carry no section numbers and the docs carry no table of contents** — both are a *delivery* concern, generated at export time (pandoc), not maintained in source.

**Heading scheme — headings are unnumbered.** All headings are plain text, with bold on H1/H2 and italics on H3:
- H1 → `# **Title**`
- H2 → `## **Title**`
- H3 → `### *Title*`

A heading's identity is its text (its name-based slug), not a position — so inserting, removing, or reordering a section renumbers nothing and breaks no anchor. The product-name H1, the doc-title H1, and the "Revision History" heading are title scaffolding. Never add a leading `N.` / `N.M` number to a heading; `/spec-build` strips any it finds.

**`use-cases.md` is a catalog grouped by area, not a hierarchical spec**, and its IDs deliberately **decouple identity from document position** (a single global sequence was abandoned because inserting one use case renumbered everything after it and broke every cross-reference). Structure: the top-level heading (Use Case List) is an unnumbered H1; under **Use Case List**, use cases are grouped under **unnumbered H2 area sub-headings** (`## **Glossary**`, `## **AI Assistants**`, …), and each use case is an **H3** heading carrying an **area-prefixed ID** — `### **UC-GLO-view-glossary: The student views…**`. The ID format is `UC-<AREA>-<slug>`, where `<AREA>` is a stable short area code (3 letters for most areas, 2 for `AI`) and `<slug>` is a short kebab-case **name-based slug** derived from the use-case name, unique within that area (no numbering, no document-order contiguity requirement). Areas, in document order — the foundation and performance-tracking areas first, then the RAM areas: `RUB` rubric, `SEC` course section, `TEA` team, `STU` student, `INS` instructor, `ACC` account/registration, `WAR` weekly activity report, `EVA` peer evaluation, then `TPL` templates/provisioning, `GLO` glossary, `DOC` requirement documents, `ART` requirement artifacts, `LNK` artifact links & tracing, `VAL` validation, `COL` collaboration, `REV` review & submission, `EXP` export, `CFG` AI configuration, `AI` AI assistants. The same `UC-<AREA>-<slug>` appears in the `UC ID and Name:` table field, and inline `UC-<AREA>-<slug>: <name>` cross-references must agree. **When adding a use case, drop it under its area** — coin a fresh name-based slug from its name (unique within the area), add the H3 block under the matching area sub-heading, and never rename or repoint an existing UC ID (the whole point is that IDs are stable handles). Need a brand-new area? Pick an unused short (preferably 3-letter) code and place it sensibly. `/spec-build` never rewrites the UC IDs; it strips stray anchors and flags **per-area** duplicate slugs and any ID↔`UC ID and Name:` mismatch. Never let any tool collapse these IDs into a global numbered sequence.

**Use-case lifecycle status (`**Status:**`).** A use case is **Active** (in MVP scope) by default, and an active use case carries **no** `**Status:**` line — absence means active. A use case that is **out of MVP scope** carries a single `**Status:**` line immediately after its `**UC ID and Name:**` line, with one of two controlled values: `**Status:** Deferred — post-MVP` (specified, but planned for a later release) or `**Status:** Tabled — future release` (parked; may be revisited, and typically left as a short stub rather than a full template). This field is the **one machine-readable marker** of deferral — `/spec-build`'s use-case structural-completeness check skips any use case whose `**Status:**` is non-Active (a deliberate stub, not a half-written UC). So **don't signal deferral only in prose or an italic lead note**: such a note may remain as human rationale, but it must be backed by the `**Status:**` field. Currently `UC-ART-promote-selection` (Tabled) and `UC-COL-collaborative-edit` (Deferred) carry it.

**Anchors are auto-generated by the renderer** (Typora, GitHub). Headings should NOT carry explicit `{#slug}` attributes — kramdown `{#id}` syntax is not honored by Typora and shows up as clutter in its Outline panel. Strip any leftover `{#xxx}` tokens. The slug the renderer computes from a heading is: lowercase the rendered text, replace whitespace with `-`, strip everything that isn't `[a-z0-9-]`, do NOT collapse consecutive hyphens. Examples: `## **Background**` → `#background`; `## **Graph-First Model**` → `#graph-first-model`; `## **Major Features / Scope**` → `#major-features--scope`. Because slugs derive from heading *text*, they stay stable when sections are inserted or reordered — but a heading **rename** changes its slug, so update inbound `[…](#old-slug)` links when you rename (`/spec-build` flags dangling ones).

**Square brackets and other Markdown-significant characters in heading text are a known trap.** Typora interprets `[...]` inside a heading as reference-link syntax and computes a non-obvious slug, even when escaped. Prefer rewriting such headings (e.g., drop the brackets) over trying to derive the matching slug. Same caution for backticks, `<>` HTML, and `!`.

**No table of contents.** The source docs carry no TOC — navigation is the editor's outline panel (Typora) and GitHub's auto-rendered heading outline, and a numbered TOC is produced at export time. If a `# **Table of Contents**` block survives in a doc, `/spec-build` removes it; don't author one.

**List style.** Use `-` (hyphen) for every unordered-list marker, in body content, at all nesting levels — not `*` or `+`.  Only convert leading list markers — never touch `*emphasis*`, `**bold**`, or `\*\*\*` placeholders.

**Glossary terms; group them thematically.** In `project-glossary.md` the section headings are unnumbered like every other doc (`# **Introduction**`, `## **Purpose**`, `# **Definitions**`), and the term headings under Definitions are likewise plain — `## **Template**`. The term list is a flat catalog whose identity is the term name, not a position (the same identity-decoupled-from-position principle as the area-prefixed IDs in `use-cases.md`): terms can be inserted or reordered freely with **no renumbering**. Related concepts must still sit next to each other — when adding a term, drop it into its thematic group, don't just append at the end. Current groups (in order) — the shared-foundation and performance-tracking groups lead, mirroring the foundation-first area order in `use-cases.md`, then the RAM groups: users & organization (team, course, course section, course admin, instructor, student); performance tracking (academic year, active week, TCU Online, weekly activity report, peer evaluation, rubric); core graph model (artifacts, types, keys, links, traceability, navigation); documents (document, document section, section key, template, authoring destination); requirement types (objective, risk, rule, feature, use case, FR, constraint, operating environment, quality attribute, external interface, glossary term, stakeholder, assumption, dependency); authoring & validation (ReqLint, keyword); AI & teaching (assistant, assistant instructions, teaching context, cross-document review criteria, project source material); acronyms & standards (MVP, FERPA, EARS, INVEST, Wiegers Requirement Categories, LLM, WCAG). Reference glossary terms by name, never by section number (e.g., "distinct from document section", not "see 2.11") — names are stable, numbers are positional and rot on every insertion. A numbered-anchor link like `[Document Section](#document-section)` works because the slug now derives from the name, not a number. Section keys (`vision.businessObjectives` etc.) are stable identifiers, unaffected by any of this.

**Glossary terms in prose use plain lowercase.** Do not bold or Title-Case glossary terms merely because they are defined terms. In ordinary prose, write `student`, `instructor`, `course admin`, `course section`, `document section`, `requirement artifact`, `artifact link`, `business objective`, `functional requirement`, and similar terms as normal lowercase text. Preserve capitalization for headings, sentence starts, acronyms and proper nouns (`RAM`, `Project Pulse`, `AI`, `FERPA`, `EARS`, `INVEST`, `WCAG`, `Wiegers`, `Socratic`), document titles (`Vision and Scope`, `Project Glossary`, `Use Cases`, `Business Rules`, `Software Requirements Specification`), UI labels, table column headings, and code identifiers or enum values (`RequirementArtifactType`, `FUNCTIONAL_REQUIREMENT`, `DERIVES_FROM`). A **use-case title reads as a sentence and is sentence-cased**: only its first word (`The`), proper nouns, and acronyms are capitalized — the glossary-term actor stays lowercase (`### **UC-RUB-create-rubric: The course admin creates a rubric**`, not `The Course Admin`). If a term names a specific document or named document view, use the document title form (`Use Cases document`, `Business Rules document`); if it names the concept in ordinary prose, use lowercase (`a use case`, `the business rules`). Artifact-type vocabulary uses two registers: lowercase in normal prose, but Title Case when functioning as a controlled label in taxonomy lists, artifact-type tables, enum mapping prose, or template/placement matrices.

**"Section" is ambiguous — never write it bare.** Two domain senses collide: course section (a Course offering that students enroll in and that groups them into teams — the Project Pulse org unit; assistants and teaching context are configured per course section) and document section (a template-defined part of a requirement document — the unit that gets locked, validated, and versioned). Always qualify a domain mention as one or the other; never leave a bare "Section"/"section" for a domain concept. The *only* unqualified "section" allowed is a document referring to its own parts ("this section captures…") and the Wiegers template's bracketed author-guidance. Note: `Section Key` is a defined term (it maps artifacts to document sections) and stays as-is; `section-based requirement document` keeps its compound adjective. Rule of thumb when classifying: course section = enrollment / instructors / students / assistant enablement / teaching context; document section = document structure / locking / validation / authoring. Related but on a different axis: authoring destination is the glossary umbrella term for "a document section or a use case" — the lockable unit an authored edit or an accepted AI candidate is applied to (e.g., the structuring assistant in UC-AI-structure-notes targets one). Use it (short form "destination") instead of coining a synonym; note a use case is a destination but is *not* a document section, so don't fold the two together.

**Cross-doc propagation.** Glossary terms, FR IDs, BR IDs, feature names, and actor names span multiple files. When you rename or restructure something in one doc, grep the *whole repo* (not just the other four core docs) before finalizing — see the dependency map below.

**Cross-document dependency map.** Requirements here are spread across files that reference each other, so a change in one place usually obligates a check elsewhere. When you change the left column, re-sync the right. Don't trust memory — run `/spec-build`, which mechanically verifies the checkable couplings (UC↔traceability rows, ID resolution across the requirement spaces, feature/BO/SM/risk coverage, non-use-case FR coverage, and QS/non-functional traceability). Note that `traceability.md` is a **sixth** coupled file beyond the five core docs; it is the most-forgotten dependency precisely because it lives outside the `requirements/` set.

**The `/spec-build` slash command** (in `.claude/commands/spec-build.md`) is the docs-internal build-and-verify pass. It mechanically normalizes only the five core requirements docs: in Phase 1 it strips section-number prefixes and stray `{#slug}` attributes from headings, removes any stale Table of Contents, and normalizes smart quotes. It then reports semantic issues in two passes — **deterministic checks including** ID resolution across every key space, cross-reference/anchor resolution, per-area UC-ID uniqueness, traceability coverage + completeness, use-case structural completeness, non-use-case FR coverage, BO/feature/risk/business-rule coverage, MVP/deferred-scope consistency, measurable quality attributes, and QS/non-functional traceability against the architecture-of-record; and **judgment checks scoped to what changed, including** undefined/unused glossary terms, terminology & convention violations, ReqLint writing issues, cross-doc drift, rule↔use-case conflicts, restated requirements, and QS threshold consistency. It verifies `traceability.md` but does not rewrite its human-maintained matrices; the sole exception is the generated business-rule enforcement index, which `/spec-build` may regenerate from forward citations. Suggest it to the user after any non-trivial structural edit; run it when they ask for a "build" / "verify" / "resync" / "check" pass. **`use-cases.md`** is handled with care: `/spec-build` never rewrites its area-prefixed UC IDs, but still strips anchors and runs the semantic + per-area uniqueness checks.

## Known quirks

- **Don't duplicate the architecture "for RAM."** The whole-product architecture — the System Context / Container views, the binding conventions, deployment, the foundation/performance-tracking and RAM component views, and the cross-cutting subsystems — lives in the single architecture-of-record, [`design/architectural-design.md`](design/architectural-design.md). The Operating Environment and constraints are owned by the SRS. Describing RAM as a module inside the Project Pulse platform is correct (see [`README.md`](README.md)); Project Pulse is the product, not RAM's "host platform" — don't frame it as a host RAM merely runs on. Author any RAM-specific addition (new SPA views, API endpoints, DB tables for the requirements graph, the LLM service as an external integration) as an extension that cites the architecture-of-record, never a fork of it.
- **Revision History tables** at the top of each doc are placeholders (`<dd/mmm/yy>`, `<x.x>`). Only fill them in when the user explicitly asks.

## Working in `docs/`

- No traditional build, lint, or test commands for the requirements docs — but the `/spec-build` slash command (see Authoring conventions above) acts as their build-and-verify pass. "Correctness" means cross-document consistency and adherence to the templates the docs themselves describe (ReqLint-style: no vague verbs like "manage"/"support", no subjective adjectives like "fast"/"user-friendly", "shall" statements for FRs, atomic and testable).
- The Use Cases doc is large. Prefer targeted reads (offset + limit, or Grep) over reading it whole.
- The `.claude/` folder at the repo root holds project-local settings and the `/spec-build`, `/design`, `/implement`, and `/sync-check` slash commands — leave it alone unless the user asks to change permissions, hooks, or commands. (`/sync-check` is the periodic **spec↔code** conformance audit — the docs↔code companion to `/spec-build`'s docs-internal checks; it records drift as `OI-n` in `requirements/OPEN-ISSUES.md`.)

## Other files under `docs/` (beyond the five core docs)

- **`traceability.md`** — the live spec→code map, the whole-project traceability home. It opens with the feature → use-case-area coverage map, then carries two realization axes plus the off-spine coverage layer: the **functional** UC ↔ FR ↔ design/code/test matrix (one row per UC, `FR IDs` column) plus its **non-use-case FR traceability** companion (`FR-<AREA>-*` → design/code/tests/build/verify), the **non-functional** quality-attribute ↔ `QS-n` ↔ test matrix (coupled to the arch-of-record's quality scenarios, which it cites by ID and whose verification state it owns), and three cross-cutting matrices: **BO measurement** (`BO-*` → `SM-*` → evaluation route/state), **risk coverage** (`RI-*` → mitigation/acceptance), and the generated **business-rule enforcement index** (`BR-*` → citing UC/FR/QS). Keep them in sync. `/design` sets a use-case row's **Build** to `📐 Designed`; `/implement` sets **Build** and fills **Verify** in its Phase 5; `/spec-build` verifies the traceability couplings and regenerates the business-rule enforcement index. The functional UC and non-use-case FR matrices carry **Build** and **Verify** as two independent columns (a built-but-untested item reads `✅ Built` / `🔎 None` rather than masquerading as done); `/sync-check` reconciles those states against the actual tests and flags `✅ Built` use cases whose negative-path tests are fewer than their extensions.
